# FX-26 compiled to native code, in KFX, as Fixpt's ladder of machines

Status: research and a plan, 2026-10-14. PLAN §9, reordered: "If the FX26
compiler and runtime in Kayak is slow, then Kayak has no purpose." The
user: the native compiler delivered "via the same series of tiered
compilers that Fixpt offers", stencils perhaps from kayak-rt's Rust; and
"you are going to have to deal with executing heap-allocated code".

Sources: Fixpt at `09acf16` (a research agent's report, `docs/research/fixpt-tiers.md`, its
claims citing Fixpt's files);
Larceny's accomplice fork (`~/Dev/LangPlay/accomplice`, read only:
`src/Rts/Sys/code-space.[ch]`, `osdep-generic.c`); Coopt at `c366857`.

## Findings first

1. **Fixpt's ladder is two code forms and nine machines.** Cellular words
   (token-threaded, Forth-like, heap bloblets of cells: a fixnum names one
   of 63 routines, a pointer names another word) and register code
   (Larceny's MacScheme machine: an accumulator, REG1–8, explicit frames;
   35 ops), both compiled from the checked tree, each compiler written
   twice (Rust, FX-26) and kept cell for cell the same. The machines, and
   fib's time (ms): the Scheme VM 123; the evaluator in FX-26 about 1400;
   cells by a Rust interpreter 135, by a hand machine of arm64 routines
   (generated by Rust at start-up, not hand-written) 17, by stencils
   (Rust routines compiled by nightly rustc with `become`, copied in) 23;
   cells compiled to arm64, by Rust or by `native.fx`, 14; register code
   to arm64 in the cellular machine's convention 6.2, in a native calling
   convention with native frames (`direct.rs`, the default) 2.8.
2. **What Fixpt has only in Rust** is most of what is fast: register code
   to arm64 (`direct.rs` 6195 lines, `cellular/regcode.rs` 1484: Fixpt's
   TODO §81), the hand machine's routines, code placement, the runtime and
   collector. In FX-26 it has the whole of stage A (`compile*.fx` 4959
   lines, `regcode*.fx` 5015), and stage B for cells only (`native.fx`,
   `arm64.fx`, 1250, about 140x slower than its Rust twin).
3. **The tiers are checked by comparing code, not only answers**: one
   layout table generating the FX-26 side's constants; one validator every
   word goes through; Rust and FX-26 compilers compared cell for cell, the
   two arm64 encoders encoding for encoding, `native.fx` against
   `assemble_word` instruction for instruction over the whole front end;
   every test program on every machine against the lowered run.
4. **Executing heap-allocated code: two precedents.**
   - *Accomplice* (Larceny, native arm64 and x86-64): a **separate code
     space**, a semispace in its own arena below the data arena, `MAP_JIT`
     on macOS (writable or executable per thread), read-write-execute on
     Linux. Code vectors hold no pointers (constants are a separate
     object), so the code space is never scanned and pointers into it are
     not remembered. Installing copies a code vector in between turning
     writing on and off for this thread (`pthread_jit_write_protect_np`,
     cheap) and flushes the instruction cache. Code is collected with the
     oldest generation, copied to a new code semispace; under the
     regional collector, by a separate pass that forwards code and fixes
     every pointer to it. Return addresses are kept relative to their code.
   - *Fixpt*: code bloblets, their fields beside their code, in a
     non-moving, mark-swept code area of the heap, **double-mapped** (a writable view and an executable view, by
     `mach_vm_remap`), since its code bloblets' fields (constants, callees,
     globals) are written often and `MAP_JIT` toggling measured 32 ns a
     write. Native frames are laid out as bloblets, with a liveness mask as
     their stack map; before a collection the native stack, which lies at
     the nursery's top, is flushed into the heap as frame objects
     (Larceny's stack cache), so the collector walks no stack.
   - *Coopt* never got there: its "code in the heap" is interpreted code
     bloblets; no crate of it maps memory executable.
5. **Fixpt's stencil machine has no holes**: its build refuses any
   relocation, so it is a copied interpreter, not a template compiler. It
   needs nightly rustc. In kayak it would be kayak-rt's (the user), Rust
   routines in the same `#[repr(C)]` state as the hand machine.

## Kayak's ladder

| tier | Fixpt's | kayak's | stage A | stage B | executes |
|---|---|---|---|---|---|
| 0 | `fx-ast-eval` | the engine (C58, C64): a CEK machine over words | lowering (`lower.kfx`) | none | KFX, as Rust |
| 1 | `fx-cells-rsinterp` | cells interpreted | KFX | none | KFX, as Rust; **the reference meaning of every tier above** |
| 2 | `fx-cells-asminterp` | the hand machine | KFX | none | arm64 routines generated by KFX (its encoder, from `arm64.fx`) |

## Decisions

1. **Fixpt's formats, taken whole**: values (3-bit tags, 61-bit fixnums),
   bloblets, words, register code, routine and op numbers, from one
   layout table, as Fixpt's `layout.rs` makes `layout.fx`. Then a word
   kayak's stage A makes can be compared with what `fixpt compile` shows,
   cell for cell, and tier by tier the answers with Fixpt's machines. The
   engine's own word format (C64) stays tier 0's.
2. **The heap's memory is flat arrays of `i64`**, as the engine's is:
   KFX reads and writes them safely; kayak-rt allocates a large one from
   reserved memory, at an address that never changes, which native code
   is given. Values are indices into it for KFX, and addresses for native
   code with a base register, until measured otherwise.
3. **Code bloblets, as Fixpt's** (its `docs/object-model.md`, "Code"
   and "A collected code area"): a procedure's code is the suffix of a
   bloblet whose fields (its constants, callees, globals, name, frame
   layout, the checker's facts) sit at fixed negative offsets from its
   first instruction, read PC-relatively; a closure, a code bloblet whose
   captured values are fields. They live in a non-moving code area of the
   heap, mark-swept within the copying collection (the collector updating
   fields in place), mapped twice: fields written through a read+write
   view, code run from a read+execute view of the same pages, so nothing
   is ever both, and no write toggles anything. This keeps the bloblet's
   point, code beside its environment (the user, 2026-10-14), which
   accomplice's pointer-free code space gives up. Accomplice's design
   (a copied code space, code reaching everything through the machine's
   state) fits only the cellular machines' compiled words, as Fixpt uses
   it there; `MAP_JIT` toggling measured 32 ns a field write (Fixpt).
   Non-moving is a choice, not a promise kept to Fixpt: FX-26's
   `seal-code` (Fixpt §97) says nothing of moving, nor does its `native`
   declaration (code reached by its reference plus `x26`, fields
   PC-relatively, the frame's return slot named in its stack map), so
   kayak's collector may yet move code (the user, 2026-10-15), if kayak's
   generators keep no raw code address the convention does not describe:
   a callee is reached through a field of the caller's code bloblet,
   loaded PC-relatively and branched to, never by a direct call; a direct
   call to a closure the collector may move is not part of the design.
4. **`unsafe` in one new crate** (`kayak-jit`, Q7): reserving and mapping
   memory (the code area's two views), writing and flushing code, the trampolines into native code and back,
   flushing native frames. Nothing else.
5. **K1 at the boundary: FX-26 extended, in Fixpt** (the user,
   2026-10-14: "we need the extensions in Fixpt"). KFX can use only what
   FX-26 has, and FX-26 has no way to place and run machine code, so
   FX-26 gains primitives for it, which Fixpt implements and kayak's
   KFX then uses: code bloblets in the double-mapped code area (made with
   fields and a suffix's size, written, sealed, made a procedure at a
   stated type under an effect of their own), and later the contract
   native code needs (value layout, registers, call-outs, frames for the
   collector, fuel) as part of FX-26's definition. Not kayak-rt standing
   in for a KFX procedure's FX-26 body, which was the other way (dropped).
   The request is the user's to send; until the pin moves, kayak's side
   (the code area, the encoder) is built against it.
6. **Made code meets kayak's values where both lay them out alike**
   (C116, 2026-10-15, once Fixpt had §97): fixnums, booleans, unit,
   characters; a bloblet of no fields sealed. The native compiler's
   object programs run in a heap of Fixpt's layout that KFX owns as data
   and collects, entered by native procedures, the convention's routines
   KFX procedures reached through fields, so that the same KFX and the
   same machine code run on Fixpt and on kayak.
7. **Each tier checked against the one below**, by code where both make
   code (cells with Fixpt's, instructions between tiers 4 and 5 where they
   overlap) and by answers on every program, as Fixpt's
   `every_program_on_every_machine`.

## Open: where stage A comes from

Fixpt's stage A compiles Fixpt's checker's trees, using its facts (types,
effects, constants: tables keyed by span). Two ways:

- **A. Fixpt's front end, through KFX.** Make KFX accept Fixpt's FX-26
  front end (143 files, 40,000 lines: reader, parser, checker, both
  compilers, `native.fx`), extending KFX where it falls short, and build
  it as kayak's. Its checker is then Fixpt's rule for rule (TODO §30
  solved by construction), its words Fixpt's by construction, and kayak
  becomes the reference by carrying Fixpt's FX-26 sources and retiring its
  Rust. The risk: what of FX-26 those files use has no Rust mapping (a
  bloblet field holding a procedure was one refusal). kfx accepts 7 of
  the 143 today; 121 stop first at a module file's form, so what lies
  behind it is not yet known.
- **B. Kayak's own front end, Fixpt's compilers ported to its trees.**
  Port `compile*.fx` and `regcode*.fx` onto kayak's checked forms and the
  facts its checker leaves (C114's comparison growing the checker beside
  them). Kayak keeps its own checker, grown in place (C114).

Either way the first step is the same: the module-file form in KFX (a
natural extension, Fixpt's front end's first refusal), then the survey of
the 143 files run again, to see what A would cost.

## Steps

1. Module files in KFX; the front end's files surveyed again (decides A
   or B).
2. The layout table, generated for KFX; the heap in Fixpt's format; tier
   1, cells interpreted, with words made by hand, then by stage A.
3. `kayak-jit`: the code space, installation, the trampoline; the arm64
   encoder in KFX (`arm64.fx`'s, checked against the system `as`, as
   Fixpt's is); tier 2, the hand machine.
4. Tier 4 (`native.fx`), tier 5 (register code), tier 6 (native frames,
   stack maps, flushing), each against the one below and against Fixpt.
5. Tier 3, the stencils, when the hand machine is there to compare with.
6. Then Twobit's passes Fixpt has not taken (A-normal form, commoning,
   copy propagation, dead code, parallel argument assignment, a frame
   peephole, register allocation), and the compiler compiled by itself
   into its own heap.
